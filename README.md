# token_monitor

Скрининг пулов и ресерч токенов для LP на BSC, Base, Robinhood Chain.

## Воронка

1. **Screener** (Codex `filterPairs`): один запрос → top-N пулов по всем сетям
2. **`classify_market`**: математика, 0 запросов → FAST / SLOW / SKIP
3. **Security** (GMGN) → `security_flags` *(этап 3)*
4. **Ручное подтверждение** в Telegram *(этап 4)*
5. **Deep research**: X, Fomo, LP Agent, LLM-сводка через Ollama *(этап 5)*

## Логика вердикта

Решение принимается не по APR, а по времени, за которое комиссии покрывают
потерю LP-позиции в стресс-сценарии. Модель задаётся `PARAM_STRATEGY`:

- `spot` / `bidask` (по умолчанию `spot`, диапазон `PARAM_STRATEGY_DEPTH`, размер
  `PARAM_STRATEGY_SIZE`): позиция ниже цены. Вердикт решают вероятные сценарии —
  падение на **¼ и ½ диапазона** (берётся худший). **Дно диапазона** маловероятно и
  на вердикт не влияет, но выводится (`cover bottom`) и используется для сортировки
  как метрика сравнения пулов. Горизонт — `PARAM_STRATEGY_HORIZON_DAYS` (2 дня).
- `fullrange`: классическая full-range позиция при падении на `PARAM_STRESS_DROP`
  (`1 − √(1 − drop)`).

- **SLOW**: объём стабилен (`min_persistence ≤ vol_4h·6 / vol_24h ≤ max_persistence`),
  и комиссии за 24ч покрывают стресс за горизонт модели (`strategy_horizon_days` или `slow_horizon_days`).
- **FAST**: при текущем темпе (последний час) стресс покрывается за `fast_horizon_hours`.
- **SKIP**: всё остальное, а также накрученный объём (wash), даже если математика проходит:
  средняя сделка > `max_trade_share` ликвидности, < `min_unique_wallets` кошельков за 24ч
  или > `max_fresh_wallets` свопов с кошельков моложе суток. Комиссии с такого объёма
  реальны, но это приманка и он исчезает вместе с ботами.

Пороги задаются в `.env` через `PARAM_*` (см. `.env.example`).

## Статусы кандидатов

`pending → approved → collected → researched`, либо `pending → rejected`.
Переходы атомарные: повторное нажатие кнопки или гонка процессов не ломает состояние.

## Запуск

```bash
python -m token_monitor screen            # FAST/SLOW, отсортировано по скорости окупаемости
python -m token_monitor screen --all      # вместе со SKIP
python -m token_monitor analyze 0x…      # все пулы токена + риск-оценка Codex
```

Screener берёт `CODEX_API_KEY`, `SCREEN_LIMIT` (≤ 200), `SCREEN_RANK_BY`,
`SCREEN_MIN_VOLUME_24H`. Пороги общие со скорингом — `PARAM_MIN_LIQUIDITY` ($10k) и
`PARAM_MIN_FEE_BPS` (100 = 1%, v2/v3) / `PARAM_MIN_FEE_BPS_V4` (50 = 0.5%). В запросе к Codex
идёт меньший из порогов комиссии (версию пула сервер не фильтрует), точный — в скоринге.

Комиссия пула: `poolFeeBps` → `pair.fee` (v3/v4, миллионные доли) → известная v2-фабрика.
Пулы с динамической комиссией и неизвестные v2-форки отбрасываются. v4-пулы с `fee = 0`
(лаунчпады, комиссию забирает хук) получают SKIP `no LP fee`.
Серверный фильтр комиссии работает по `poolFeeBps` и теряет пулы, где он не заполнен, но без
него top-N занимают 1bp мажор-пулы (на топ-200: 200 пулов ≥1% против 3). `analyze` его не
использует — там порог применяется в скоринге с причиной `fee X% < 1% (v3)`.
Пары из двух базовых активов (WETH, WBNB, стейблы, BTC-обёртки; по символу) в скрининг
не попадают; в паре мем/базовый целевым считается мем.

## Сценарии LP-стратегий

```bash
python -m token_monitor analyze <CA> --strategy spot   --depth 0.7 --size 1000 --scenarios 2
python -m token_monitor analyze <CA> --strategy bidask --depth 0.7 --size 1500 --scenarios 2
python -m token_monitor screen --strategy bidask
```

Позиция в quote (ETH/BNB/USD) в диапазоне от цены входа до −depth: `spot` — равный капитал
по бинам, `bidask` — капитал растёт к нижней границе. Таблица по уровням цены: доля в токене,
средняя цена выкупа, PnL позиции без комиссий, комиссии/день и сколько дней стоять на этом
уровне, чтобы комиссии покрыли PnL. Стоимость v3/v4-позиции зависит только от текущей цены,
поэтому частичный откат — это подъём по той же таблице.

Допущения: ликвидность пула = full-range эквивалент TVL (оптимистично, если другие LP
сконцентрированы у цены); объём в токенах постоянен (в $ падает вместе с ценой).

## LP-позиции

```bash
python -m token_monitor position https://app.uniswap.org/positions/v3/base/6093665 \
                                 https://app.uniswap.org/positions/v4/robinhood/3318457
```

Позиции v3/v4 читаются напрямую с блокчейна (JSON-RPC, без web3): диапазон в цене целевого токена,
где цена внутри диапазона, состав, PnL от верхней границы, несобранные и собранные комиссии, итог,
дата входа и фактическая доходность в день, реальная доля в активной ликвидности пула.

- Собранные комиссии: v3 — L·(feeGrowthInside сейчас − на минте), один архивный вызов;
  v4 — `ModifyLiquidity` с нулевой дельтой + переводы от PoolManager в той же транзакции.
  Токенная часть клеймов оценивается по цене на момент клейма.
- Объём пула — DexScreener (бесплатно), $-цены ETH/BNB и исторические цены — один запрос к Codex.
- RPC переопределяется `RPC_<СЕТЬ>`; `--no-entry` пропускает историю (быстрее).

## Проверка дева

```bash
python -m token_monitor dev <CA> [--days 7]
```

Реальный запускатор — отправитель транзакции, в которой токен сминтился (Codex часто показывает
«деплоером» контракт лаунчпада). Команда показывает: сколько дев купил на старте и держит сейчас,
куда вывел токены (контракты — продажа в пулы, кошельки — раздача, чтобы спрятать долю), и его другие
запуски за `--days` по событию лаунчпада из транзакции создания, с капитализацией из Codex.
Флаги: покупка ≥5% на старте, держит ≥5%, вывел ≥1% на кошельки, ≥5 запусков.
Нужен RPC с `eth_getLogs` (публичный bsc-dataseed его не отдаёт — `RPC_BSC=...`).
